1. **先读内核文档的概念**：打开上游 [usage-model.rst](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/Documentation/devicetree/usage-model.rst?h=v6.17.7)，先读开头的 Data Model、2.1 High Level View，以及 2.3 Runtime configuration、2.4 Device population。重点回答 DT 为什么是数据、Linux 用它做哪些事。
2. **看一份实际板级 DTS**：从 [rk3566-anbernic-rg353ps.dts](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/arch/arm64/boot/dts/rockchip/rk3566-anbernic-rg353ps.dts?h=v6.17.7) 开始。先看根节点 `compatible`、`model` 和 `#address-cells`，再找 `&uart`、`&i2c` 等引用；继续追踪它 include 的 `.dtsi`，观察 SoC 节点、地址、中断与状态如何补全。这里选它作为阅读样例，不代表你的目标板就是 Rockchip。
3. **追踪扁平 DTB 如何进入内核**：在 [fdt.c](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/drivers/of/fdt.c?h=v6.17.7) 阅读 `early_init_dt_verify()`、`early_init_dt_scan_nodes()`、`unflatten_device_tree()`。先用编辑器查符号，不要从文件第一行逐行读。
4. **看架构启动代码在哪里调用它**：在 [setup.c](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/arch/arm64/kernel/setup.c?h=v6.17.7) 搜索 `early_init_dt_scan` 和 `unflatten_device_tree`，把调用点放回 arm64 启动顺序中理解。
5. **最后看设备如何从节点变成内核设备**：阅读 [platform.c](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/drivers/of/platform.c?h=v6.17.7) 的 `of_platform_populate()` 和 `of_platform_default_populate_init()`；之后再学习 `compatible` 与驱动匹配。

### 关键源码摘录：DTB 到运行时节点

摘自 Linux v6.17.7 `drivers/of/fdt.c` 的 `unflatten_device_tree()`，保留核心调用：

```c
void __init unflatten_device_tree(void)
{
	void *fdt = initial_boot_params;

	/* ... */
	__unflatten_device_tree(fdt, NULL, &of_root,
				early_init_dt_alloc_memory_arch, false);
	/* ... */
}
```

阅读要点：

- `initial_boot_params` 指向启动时传入的扁平设备树（FDT/DTB）数据。
- `__unflatten_device_tree()` 将扁平二进制树转换为内核可遍历的 `struct device_node` 树；`of_root` 是运行时树的根节点。
- 这一步是“解析成内核节点”，本身还不等于每个节点都已绑定驱动。
- 可以在 VS Code 中打开 `linux/drivers/of/fdt.c`，搜索 `unflatten_device_tree`，再用 F12 跳到 `__unflatten_device_tree` 的定义。

### 关键源码摘录：从设备树节点创建 platform device

摘自 Linux v6.17.7 `drivers/of/platform.c` 的 `of_platform_populate()`，只保留遍历和创建部分：

```c
for_each_child_of_node_scoped(root, child) {
	rc = of_platform_bus_create(child, matches, lookup, parent, true);
	if (rc)
		break;
}
```

阅读要点：这里展示设备树节点到 platform device 创建流程的入口。继续在同一文件追踪 `of_platform_bus_create()`，观察它怎样检查节点、递归总线并调用设备创建函数。之后驱动匹配是另一段流程，不要把“创建设备”和“驱动成功 probe”混为一件事。

## 学习目标

理解设备树要描述什么、为什么 Linux 需要它，以及它怎样交给内核。

## 设备树解决的问题

Linux 内核需要知道当前板子有哪些硬件，以及这些硬件的资源和连接方式。例如：

- 某个 UART 控制器的寄存器地址范围和中断号
- 哪个 I2C 控制器连接了哪些设备
- GPIO 控制器、时钟、复位和引脚复用关系
- 内存范围、CPU 等基础硬件信息

这些板级信息如果全部写死在内核源码里，每种板子都要维护一套专属代码，内核会难以复用。设备树把大部分板级硬件描述从内核代码中分离出来，作为数据交给内核。

设备树描述的是硬件布局和资源，不是外设驱动本身。驱动仍由内核代码实现；内核根据设备树中的描述识别并创建设备，再让匹配的驱动负责操作它。

## 启动流程中的位置

一个简化的启动过程如下：

1. Boot ROM 和 Bootloader 完成早期启动工作。
2. Bootloader 将 Linux 内核镜像和设备树二进制文件（DTB）放入内存。
3. Bootloader 把 DTB 的位置等启动信息交给内核。
4. 内核解析设备树，获得内存、CPU、控制器和板级设备等信息。
5. 内核中的总线/设备模型创建设备，并尝试与驱动匹配。

常见文件格式：

- **DTS**：人编写的设备树源文件。
- **DTSI**：可被其他设备树包含的公共片段。
- **DTB**：编译后的二进制设备树，启动时由 Bootloader/内核使用。
- **DTC**：设备树编译器，常用于 DTS 与 DTB 之间的编译/反编译。

## 简化示意

```text
板级硬件信息（DTS/DTSI）
          │ DTC 编译
          ▼
         DTB ──Bootloader 传给内核──▶ Linux 内核解析
                                           │
                                           ▼
                               创建设备并匹配已有驱动
```

## 关键边界

- 设备树是对硬件的描述，不是驱动程序。
- 设备树本身不会“启动”硬件；驱动根据设备树提供的信息去配置和控制硬件。
- 设备树通常描述静态板级信息。运行时动态变化的设备也可能由其他机制发现，例如 USB 设备枚举。
- 具体属性的含义由设备树绑定（binding）和对应子系统/驱动约定，不能只凭属性名字猜测。

## CPU 拓扑：`cpus` 与 `cpu-map`

`/cpus` 是根节点下描述处理器节点的容器。每个 `cpu@...` 子节点描述一个逻辑 CPU（包含 CPU 类型、硬件标识 `reg`、启用方法等）。需要表达多核层级/异构簇拓扑时，可在 `cpus` 下增加 `cpu-map`，通过 phandle 把拓扑位置映射到具体 CPU 节点。

拓扑节点的层级可按平台需要使用：

```text
/cpus
└── cpu-map                 固定节点名
    └── socketN             可选插槽层
        └── clusterN        可选集群层，可有多个
            └── coreN       核心层
                └── threadN 可选硬件线程层
                    └── cpu = <&cpuX>
```

- `cpu-map` 必须叫这个名字，且是 `cpus` 的子节点。
- `socketN`、`clusterN`、`coreN`、`threadN` 使用固定前缀加数字编号；编号在同一父节点下用于区分兄弟节点。拓扑层级要按实际处理器组织，不要求每个平台都出现 socket/cluster/thread 全部层级。
- 每个 `coreN` 通常用 `cpu = <&cpuX>;` 指向一个 `cpu@...` 节点。若一个核心包含多个硬件线程，则在 `coreN` 下用 `threadN` 子节点分别引用逻辑 CPU。
- 大小核等异构系统通常用不同 cluster 表达不同 CPU 簇；`cpu-map` 描述拓扑关系，CPU 的具体型号仍在各 `cpu@...` 节点中描述。

Rockchip RK3399（Cortex-A53 + Cortex-A72）真实片段，摘自 Linux v6.17.7 `linux/arch/arm64/boot/dts/rockchip/rk3399-base.dtsi`：

```dts
cpus {
    #address-cells = <2>;
    #size-cells = <0>;

    cpu-map {
        cluster0 { /* Cortex-A53 小核簇 */
            core0 { cpu = <&cpu_l0>; };
            core1 { cpu = <&cpu_l1>; };
            core2 { cpu = <&cpu_l2>; };
            core3 { cpu = <&cpu_l3>; };
        };

        cluster1 { /* Cortex-A72 大核簇 */
            core0 { cpu = <&cpu_b0>; };
            core1 { cpu = <&cpu_b1>; };
        };
    };

    cpu_l0: cpu@0 {
        device_type = "cpu";
        compatible = "arm,cortex-a53";
        reg = <0x0 0x0>;
    };
    /* 其他 cpu@... 节点省略 */
};
```

注意：这个 RK3399 实例没有 `socketN`，因为该 SoC 的设备树无需额外插槽层。`cpu-map` 里的 `cluster0/core0` 通过 `cpu = <&cpu_l0>` 对应到下面实际定义的 CPU 节点；两者不是重复描述，而是“拓扑位置”与“CPU 实体属性”的关联。

## GPIO：控制器端与使用端

GPIO 控制器节点由 SoC/芯片 BSP 描述，外设节点引用 GPIO。常见控制器属性：

- `gpio-controller;`：布尔属性，声明本节点是 GPIO provider。
- `#gpio-cells = <N>;`：声明 consumer 的 GPIO specifier 中，phandle 后面需要多少个 32 位 cell；cell 的具体意义由该 GPIO 控制器 binding 规定。Rockchip 常见两个 cell：GPIO bank 内引脚编号和极性/标志。
- `gpio-ranges`：把 GPIO 控制器的 GPIO 编号范围映射到 pinctrl 控制器的引脚编号范围，参数解释按 GPIO/pinctrl binding。

Rockchip RK3568 GPIO 控制器实例，摘自 `linux/arch/arm64/boot/dts/rockchip/rk356x-base.dtsi`：

```dts
gpio0: gpio@fdd60000 {
    compatible = "rockchip,gpio-bank";
    reg = <0x0 0xfdd60000 0x0 0x100>;
    interrupts = <GIC_SPI 33 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&pmucru PCLK_GPIO0>, <&pmucru DBCLK_GPIO0>;
    gpio-controller;
    gpio-ranges = <&pinctrl 0 0 32>;
    #gpio-cells = <2>;
    interrupt-controller;
    #interrupt-cells = <2>;
};
```

外设使用端示例：

```dts
sensor@38 {
    compatible = "vendor,touch-controller";
    reg = <0x38>;

    touch-gpios = <&gpio0 RK_PB5 GPIO_ACTIVE_HIGH>;
    reset-gpios = <&gpio0 RK_PB6 GPIO_ACTIVE_LOW>;
};
```

`touch-gpios`、`reset-gpios` 遵循常见 `*-gpios` consumer 命名约定；`data-gpios` 也可作为驱动 binding 定义的自定义属性。消费者驱动通过 GPIO descriptor API 按 connection ID（例如 `touch`、`reset` 或 `data`）获取，不应假定属性名任意写都能被驱动识别。上例中的 `RK_PB5`、`GPIO_ACTIVE_LOW` 等宏需包含对应 Rockchip/GPIO 头文件，并以目标 DTS binding 为准。

## pinctrl：服务端/provider 与客户端/consumer

Pin multiplexing（pinmux，引脚复用）是把同一物理管脚配置为 GPIO、UART、I²C、SPI 等功能之一；pinctrl 子系统还可配置上拉/下拉、驱动强度等电气属性。SoC pinctrl 驱动通常由芯片原厂 BSP 提供；外设/板级 DTS 使用 pinctrl state 请求所需引脚功能。这样驱动通常不需要自行改写 SoC 的管脚复用寄存器。

- **服务端/provider**：SoC pin controller 节点及其 pin group/function/pin configuration。组内语法、属性名经常是芯片厂商专用的，例如 Rockchip 的 `rockchip,pins`。
- **客户端/consumer**：UART、LED、I²C 等需要管脚配置的设备节点，通过 `pinctrl-names` 命名状态、`pinctrl-0` 等引用 provider 中定义的状态节点。`default` 是常见默认状态名；设备可按 binding 定义 `sleep` 等其他状态。

RK3568 GPIO LED 的板级消费者示例，摘自 Linux v6.17.7 `linux/arch/arm64/boot/dts/rockchip/rk3568-radxa-cm3i.dtsi`：

```dts
/ {
    gpio-leds {
        compatible = "gpio-leds";

        led_user: led-0 {
            gpios = <&gpio0 RK_PA6 GPIO_ACTIVE_HIGH>;
            function = LED_FUNCTION_HEARTBEAT;
            color = <LED_COLOR_ID_GREEN>;
            linux,default-trigger = "heartbeat";
            pinctrl-names = "default";
            pinctrl-0 = <&led_user_en>;
        };
    };
};
```

对应的 RK3568 pinctrl provider 配置摘自同一文件：

```dts
&pinctrl {
    leds {
        led_user_en: led_user_en {
            rockchip,pins = <0 RK_PA6 RK_FUNC_GPIO &pcfg_pull_none>;
        };
    };
};
```

解读：`&pinctrl` 下定义服务端 pin group `led_user_en`，选 GPIO bank 0 的 PA6，复用功能设为 GPIO，并引用无上下拉配置；LED consumer 同时用 `gpios` 描述 GPIO 控制和极性，用 `pinctrl-0` 选择 pinctrl state。板级节点的 GPIO 极性、电路有效电平和 pinmux 必须结合原理图核对。不要将 Rockchip 专用 `rockchip,pins` 写法当成跨芯片通用语法。

### 源码阅读顺序

1. CPU 拓扑：先读 `Documentation/devicetree/bindings/arm/cpus.yaml` 中 ARM CPU 节点约束，再对照 `rk3399-base.dtsi` 的 `cpu-map` 和 CPU 节点。
2. GPIO：对照 `rk356x-base.dtsi` 的 GPIO bank 节点、`Documentation/devicetree/bindings/gpio/` 下对应 binding，再看 LED/touch consumer 的 `*-gpios` 属性。
3. pinctrl：先读 `Documentation/devicetree/bindings/pinctrl/pinctrl-bindings.txt` 的 client states，再对照 `rk3568-pinctrl.dtsi` 中 provider pin group 与 `rk3568-radxa-cm3i.dtsi` 的 LED consumer。
4. 接着追踪 GPIO descriptor 和 pinctrl state 的驱动 API；当前阶段先建立 DTS 引用关系，不要求立即读完底层寄存器实现。
